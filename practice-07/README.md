## Результат

Реализовано React-приложение для управления списком задач и категориями с полным циклом операций: отображение карточек с названиями категорий и локализованными приоритетами, создание и редактирование с валидацией полей, переключение статуса, удаление с подтверждением (`window.confirm`), совместная фильтрация по поиску, статусу, приоритету и категории, расчёт общей статистики и количества найденных записей, а также разделение пустого списка и отсутствия совпадений по фильтру.

**Ограничения хранения в памяти:** массив `tasks` хранится только в состоянии React (`useState`) внутри текущей вкладки. После перезагрузки страницы исходный замороженный набор из `src/data.js` и начальный фильтр варианта восстанавливаются заново — это ожидаемое поведение ПР7 до подключения HTTP API в ПР8.

## Компоненты и состояние

- **Владельцы состояния:**
  - `App` (`src/App.jsx`) владеет общим состоянием приложения: `tasks` (копия исходного набора), `filters` (инициализируется через `createInitialFilters()`), `editingId` (`null` или числовой `id` редактируемой задачи) и `notice` (текст и тип статусного уведомления). Справочник `categories` импортируется как неизменяемые данные.
  - `TaskForm` (`src/components/TaskForm.jsx`) владеет локальным состоянием формы: `draft` (`title`, `priority`, `categoryId`), `errors` (ошибки валидации по полям) и `saveError` (ошибка при отказе сохранения).
- **Передача данных и обратных вызовов:** данные передаются сверху вниз через `props` (`stats`, `filters`, `categories`, `visibleTasks`, `initialTask`), а пользовательские действия поднимаются наверх через коллбэки (`onChange`, `onSave`, `onCancel`, `onToggle`, `onEdit`, `onDelete`).
- **Неизменяемые обновления и производные данные:** все изменения `tasks` выполняются чистыми функциями из `src/domain/task-service.js` (`addTask`, `updateTask`, `toggleTask`, `removeTask`), возвращающими новый массив и новые объекты без мутации аргументов. `visibleTasks`, `stats` и `editingTask` вычисляются прямо при рендере без дополнительных `useState` и `useEffect`.
- **Ключи и сброс формы:** элементы списка в `TaskList` получают стабильный ключ `key={task.id}`. Компонент `TaskForm` получает `key={editingId ?? 'new'}`: при переключении между задачами или возврате к режиму создания React пересоздаёт экземпляр формы, автоматически сбрасывая `draft`, `errors` и `saveError`. При `onSave` возвращается `true`/`false`: черновик очищается только при успешном сохранении.
- **Дополнительное задание:** вынесен отдельный компонент `StatusMessage.jsx` с различимыми состояниями успеха/информации (`role="status"`) и ошибки (`role="alert"`), а также добавлен файл `checks/workflow.test.js` с автоматическими проверками полного жизненного цикла «создание → редактирование → переключение → удаление», сценария Варианта 1 и пересоздания после полной очистки списка.

## Контрольные вопросы

1. **Чем JSX отличается от строки HTML?** JSX — синтаксическое расширение JavaScript, компилируемое в вызовы создания React-элементов (`React.createElement` / `jsx`); выражения в `{}` безопасно экранируются, а вместо HTML-атрибутов используются свойства вроде `className` и `htmlFor`.
2. **Чем props отличаются от состояния?** `props` — входные данные, передаваемые родителем и доступные только для чтения; состояние (`useState`) принадлежит самому компоненту и может изменяться во времени, вызывая повторный рендер.
3. **Почему изменение обычной переменной не заменяет `useState`?** Локальная переменная пересоздаётся при каждом вызове функции компонента, а её изменение не уведомляет React о необходимости перерисовать интерфейс.
4. **Когда требуется функциональная форма обновления состояния?** Когда новое состояние вычисляется на основе предыдущего (например, изменение массива `tasks` или инкремент счётчика), чтобы гарантировать работу с актуальным значением при пакетных обновлениях.
5. **Почему нельзя менять объект задачи внутри поверхностной копии массива?** Поверхностная копия массива копирует только ссылки на объекты; мутация элемента меняет исходный объект, ломает чистоту рендера и может не быть обнаружена React при сравнении ссылок.
6. **Для чего списку стабильный `key` и почему индекс здесь не подходит?** `key` помогает React сопоставлять элементы между рендерами; при удалении или фильтрации индексы сдвигаются, что приводит к ошибочному переиспользованию DOM-узлов и локального состояния.
7. **Почему видимая выборка и статистика не хранятся в отдельных состояниях?** Они полностью вычисляются из `tasks` и `filters`; дублирование в отдельных `useState` создаёт риск рассинхронизации после каждого действия.
8. **Как дочерний компонент сообщает родителю о действии?** Вызывая функцию обратного вызова, переданную через `props` (например, `onToggle(task.id)` или `onSave(value)`).
9. **Что делает поле управляемым?** Его значение задаётся из состояния React (`value={...}`), а каждое изменение пользователя обновляет это состояние через обработчик `onChange`.
10. **Почему `categoryId` из `select` требует преобразования?** Значение любого DOM-элемента `<select>` всегда строка, тогда как в модели задачи `categoryId` — положительное целое число.
11. **Как меняется состояние формы при изменении её ключа?** При смене `key` React размонтирует старый экземпляр компонента и монтирует новый, инициализируя `useState` заново.
12. **Почему подтверждение удаления не помещается внутрь функции обновления?** Функции обновления `setState` должны быть чистыми: в `StrictMode` React может вызывать их дважды, что привело бы к повторному открытию диалога `confirm`.
13. **Как отличить отсутствие задач от отсутствия совпадений фильтра?** Сравнить общую длину массива `tasks.length` (`totalCount === 0`) с длиной отфильтрованного массива `visibleTasks.length === 0`.
14. **Что проверяет `npm test` и чего он не проверяет?** `npm test` проверяет чистую бизнес-логику в `task-service.js` (валидацию, фильтрацию, статистику, иммутабельные операции), но не рендерит JSX-компоненты, не проверяет DOM-события, доступность и работу браузера.
15. **Какие части приложения потребуется изменить для подключения API в ПР8?** Заменить синхронное локальное хранилище в `App` на асинхронные запросы через HTTP-клиент (`useEffect` для начальной загрузки и фильтрации с отменой, асинхронный `onSave` возвращающий Promise), добавить состояния `loading`/`error` и блокировку кнопок на время сетевых мутаций.

## Вывод

Освоено построение компонентного интерфейса на React и Vite с чётким разделением чистой доменной логики (`task-service.js`) и представления (`App`, `TaskStats`, `TaskFilters`, `TaskForm`, `TaskList`, `TaskItem`, `StatusMessage`). На практике применены однонаправленный поток данных, иммутабельные обновления массивов и объектов, управляемые формы, сброс состояния через `key` и вычисление производных данных без лишних эффектов. В ПР8 потребуется перевести обработчики `App` на асинхронный HTTP API и добавить состояния загрузки и обработки сетевых ошибок.
