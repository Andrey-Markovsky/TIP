## Цель и результат

**Цель работы** — освоить обработку HTTP-запросов на стороне сервера с использованием Node.js и Express: маршрутизацию, разбор и валидацию параметров пути и запроса, фильтрацию данных и формирование единого JSON-контракта ответов и ошибок.

**Фактически реализованный результат:**
- реализован собственный Express-сервер с операциями чтения (`GET /api/health`, `GET /api/categories`, `GET /api/tasks`, `GET /api/tasks/:id`);
- реализована строгая валидация идентификаторов (`parsePositiveId`) и query-параметров (`parseFilters`) с поддержкой `completed`, `priority`, `categoryId` и `q`, объединяемых через логическое И без мутации исходных данных;
- отклоняются некорректные, повторяющиеся и неизвестные параметры запроса (`400 INVALID_QUERY`), неверные идентификаторы (`400 INVALID_ID`), отсутствующие записи (`404 TASK_NOT_FOUND` с `details.id`), неизвестные пути (`404 ROUTE_NOT_FOUND`) и неподдерживаемые методы на известных маршрутах (`405 METHOD_NOT_ALLOWED` с заголовком `Allow: GET, HEAD, OPTIONS`);
- поддерживаются `HEAD` (заголовки без тела), `OPTIONS` (`204` и CORS-заголовки) и скрытие внутренних деталей при `500 INTERNAL_ERROR`;
- все 90 автоматических проверок (38 модульных и 52 HTTP) пройдены успешно.

## Реализация

**Распределение обязанностей между модулями:**
- `src/validation.js` — чистая валидация и нормализация строковых входных параметров (`parsePositiveId`, `parseFilters`) без доступа к `req`/`res`.
- `src/task-service.js` — чистые функции выборки и поиска по переданному массиву (`selectTasks`, `findTask`), не зависящие от HTTP и не изменяющие входные массивы.
- `src/store.js` — создание изолированной копии исходных данных из `src/data.js` для каждого экземпляра приложения (`listTasks`, `getTask`, `listCategories`).
- `src/routes.js` — связывание HTTP-маршрутов Express (`/health`, `/categories`, `/tasks`, `/tasks/:id`) с валидацией и хранилищем, формирование ответов `{ data, meta }` и обработка `405` для неподдерживаемых методов.
- `src/app.js` — фабрика `createApp()`, настраивающая Express (отключение `x-powered-by` и `etag`, регистрочувствительная маршрутизация), общие заголовки/CORS, ранний ответ на `OPTIONS`, подключение роутера на `/api`, обработчик `404` и централизованный `errorHandler` без открытия порта.
- `src/server.js` — чтение и проверка порта (`argv` → `API_PORT` → `5505`) и запуск прослушивания на `127.0.0.1`.

**Ключевые технические механизмы:**
- **Нормализация `false`:** `Boolean('false')` даёт `true`, поэтому в `parseFilters` выполняется строгая проверка `rawCompleted === 'true' || rawCompleted === 'false'` и явное преобразование `rawCompleted === 'true'`. В `selectTasks` отсутствие фильтра проверяется через `filters.completed !== null`, а не `if (filters.completed)`.
- **Контроль дубликатов query:** вместо `req.query` используется `new URL(req.originalUrl, 'http://localhost').searchParams`. Для каждого имени проверяется принадлежность к списку разрешённых параметров и условие `searchParams.getAll(key).length > 1` — любые повторы (даже с одинаковыми значениями) дают `400 INVALID_QUERY`.
- **Проверка `id`:** `parsePositiveId` проверяет всю строку регулярным выражением `/^[1-9]\d*$/` (отсекая `0`, `-1`, `01`, `1.5`, `1e2`, `4abc`, пробелы) и дополнительно проверяет `Number.isSafeInteger(value)`.
- **Порядок middleware:** 1) общие заголовки, CORS и `OPTIONS → 204`; 2) `Router` с `GET`-маршрутами (которые автоматически обслуживают `HEAD`); 3) `router.all` для четырёх известных путей → `405` с `Allow` (строго после `GET`, иначе чтение было бы заблокировано); 4) обработчик неизвестных путей → `404 ROUTE_NOT_FOUND`; 5) обработчик ошибок с 4 аргументами `(error, req, res, next)` в самом конце.

## Контракт

**Реализованные маршруты:**
- `GET /api/health` → `200`, `{ data: { status: "ok" } }`
- `GET /api/categories` → `200`, `{ data: category[], meta: { total } }`
- `GET /api/tasks` → `200`, `{ data: task[], meta: { total, filters } }`
- `GET /api/tasks/:id` → `200`, `{ data: task }`
- `HEAD` для тех же путей → статус и заголовки как у `GET`, без тела
- `OPTIONS` для любого пути → `204`, CORS-заголовки без тела

**Пример успешного ответа (`GET /api/tasks/4`, статус `200`):**

```json
{
  "data": {
    "id": 4,
    "title": "Подготовить модель задач",
    "completed": false,
    "priority": "high",
    "categoryId": 2
  }
}
```

**Примеры ошибок (`400`, `404`, `405`):**

```json
// 400 Bad Request (GET /api/tasks?completed=0)
{ "error": { "code": "INVALID_QUERY", "message": "Параметр completed должен быть true или false." } }

// 404 Not Found (GET /api/tasks/2)
{ "error": { "code": "TASK_NOT_FOUND", "message": "Задача с id 2 не найдена.", "details": { "id": 2 } } }

// 405 Method Not Allowed (POST /api/tasks, заголовок Allow: GET, HEAD, OPTIONS)
{ "error": { "code": "METHOD_NOT_ALLOWED", "message": "Для этого ресурса доступны только GET, HEAD и OPTIONS." } }
```

**Значение `meta.total`:** поле отражает количество задач в текущей отфильтрованной выборке (`data.length`), а не общий размер всего хранилища (без фильтров оно равно 12, при пустой выборке — 0 со статусом `200`).

**Граница между ПР9 и ПР10:** в ПР9 реализуется только безопасное чтение данных из памяти процесса и базовый HTTP-контракт ошибок/методов; операции записи (`POST`, `PATCH`, `DELETE`), валидация тела запроса, проверка существования категории при записи и полноценная интеграция с React-клиентом ПР8 относятся к ПР10.

## Исправленный дефект

- **Симптом:** при первоначальной проверке заготовки все запросы к `/api/categories`, `/api/tasks` и `/api/tasks/:id` возвращали `501 NOT_IMPLEMENTED`, а при реализации фильтрации важно было избежать типичного дефекта с разбором query через `req.query` Express, при котором пустые/повторяющиеся параметры обрабатываются как массивы или теряют исходную семантику, и не допустить пропуска `completed=false` через проверку `if (filters.completed)`.
- **Причина:** в заготовке стояли заглушки `notImplemented(...)`, а стандартный парсер `req.query` не даёт такого же предсказуемого строгого контроля над повторениями и сырым набором ключей, как `URLSearchParams`.
- **Исправление:** реализован разбор `new URL(req.originalUrl, 'http://localhost').searchParams` с явной проверкой `searchParams.getAll(key).length > 1`, строгим сравнением `rawCompleted === 'true'` / `'false'` и проверкой `filters.completed !== null` в `selectTasks`, а обработчики `405` (`router.all`) зарегистрированы строго после `GET`-маршрутов.
- **Повторная проверка:** после исправления повторный прогон `npm test` прошёл с результатом `90/90` (`38/0` модульных и `52/0` HTTP).

## Контрольные вопросы

1. **Чем JavaScript в Node.js отличается от JavaScript в браузере?** В Node.js отсутствует DOM, `window`, `document` и `localStorage`, зато доступны серверные API среды выполнения: файловая система, сеть (`node:http`), процессы (`process.argv`, `process.env`), потоки и буферы.
2. **Что определяет выбор маршрута: путь, query или HTTP-метод?** Выбор маршрута определяет пара **HTTP-метод + путь (pathname)**; query-строка не участвует в сопоставлении маршрута и читается уже внутри выбранного обработчика.
3. **Чем `req.params` отличается от query-параметров?** `req.params` содержит именованные сегменты самого пути ресурса (например, `:id` в `/tasks/:id`), а query-параметры идут после `?` и задают опциональные модификаторы вроде фильтрации и поиска.
4. **Почему строка `'false'` требует явного преобразования?** В JavaScript любая непустая строка при приведении к булеву типу (`Boolean('false')`) истинна (`true`), поэтому нужно явно проверить допустимые значения `'true'`/`'false'` и вычислить `raw === 'true'`.
5. **Зачем проверять весь id и `Number.isSafeInteger`?** Регулярное выражение `/^[1-9]\d*$/` отсекает хвосты вроде `4abc`, ведущие нули `01`, дроби и отрицательные числа, которые пропустил бы `parseInt`, а `Number.isSafeInteger` защищает от потери точности при числах больше `2^53 - 1`.
6. **Почему пустая выборка имеет статус 200, а отсутствующая задача — 404?** Ресурс коллекции `/api/tasks` существует и запрос выполнен успешно — просто ни один элемент не подошёл под фильтр (`200`, `data: []`). Ресурс `/api/tasks/2` как отдельный объект не существует, поэтому возвращается `404`.
7. **В чём различие `TASK_NOT_FOUND` и `ROUTE_NOT_FOUND`?** `TASK_NOT_FOUND` означает, что маршрут `/api/tasks/:id` найден и id корректен, но в хранилище нет задачи с таким id (в `details` передаётся `{ id }`); `ROUTE_NOT_FOUND` означает обращение к несуществующему пути API.
8. **Чем 405 отличается от 404 и зачем нужен `Allow`?** `404` сообщает, что сам ресурс/путь не найден; `405` сообщает, что путь существует, но запрошенный HTTP-метод для него запрещён. Заголовок `Allow` по стандарту HTTP перечисляет разрешённые для этого пути методы.
9. **Что означает `meta.total` при активных фильтрах?** Количество задач, попавших в текущую возвращённую выборку (`data.length`), а не общее число задач в хранилище.
